# Bear Game — постоянные правила работы Codex

## 1. Главный принцип

Bear Game — рабочий production-проект.

Основной репозиторий:
lenivkodenis/Bear_game

Основная ветка исходников:
main

Production Web автоматически строится из main через GitHub Actions.

Схема:

main
→ GitHub Actions
→ flutter analyze
→ flutter test
→ flutter build web --release
→ web-deploy
→ Timeweb App Platform
→ https://bearmath.ru

Ветка web-deploy является СГЕНЕРИРОВАННОЙ.

НИКОГДА не редактировать web-deploy вручную.
НИКОГДА не использовать web-deploy как исходную ветку разработки.


## 2. Что делать В НАЧАЛЕ каждой задачи

Перед изменением файлов:

1. Прочитать этот AGENTS.md.

2. Выполнить:
   git status
   git branch --show-current
   git remote -v

3. Проверить наличие:
   - незакоммиченных изменений;
   - untracked-файлов;
   - незавершённой предыдущей работы.

4. Если есть чужие или непонятные незакоммиченные изменения:
   НЕ удалять,
   НЕ откатывать,
   НЕ перезаписывать их.
   Сначала сообщить пользователю.

5. Если сеть доступна:
   выполнить
   git fetch origin --prune

6. Перед началом изменений убедиться,
   что работа ведётся от актуального состояния main.

7. Если локальный main отстаёт от origin/main
   или история разошлась:
   НЕ выполнять destructive-операции автоматически.
   Сначала разобраться и сообщить пользователю.

8. Перед изменениями понять текущую реализацию задачи:
   не переписывать существующую механику или дизайн,
   если пользователь просит локальную правку.


## 3. Запрещённые действия без явного разрешения пользователя

Нельзя самостоятельно выполнять:

- git reset --hard;
- git clean -fd;
- force push;
- удаление веток;
- удаление больших групп ассетов;
- восстановление старой версии поверх main;
- переключение main на старую backup/restore ветку;
- массовое переписывание истории Git;
- изменение домена;
- изменение Timeweb;
- изменение S3;
- изменение GitHub Actions/deploy-web.yml;
- изменение схемы deployment;
- ручное редактирование web-deploy.

Если кажется, что такое действие необходимо —
остановиться и объяснить пользователю почему.


## 4. Правила изменения игры

При любой задаче:

- менять только то, что относится к запросу пользователя;
- не делать попутный редизайн;
- не менять механику без необходимости;
- сохранять существующий визуальный стиль;
- сохранять существующие уровни и ассеты;
- не заменять полноценную графику placeholder-графикой;
- не удалять рабочие ассеты ради оптимизации без разрешения;
- не менять имена/структуру runtime-ассетов без необходимости.

Особое внимание:
Bear Game ранее уже был случайно опубликован из старой placeholder-версии.
Этого больше нельзя допускать.


## 5. Ассеты

Если задача касается изображений, персонажей, фонов,
анимаций, JSON или видео:

перед завершением проверить:

- файл действительно существует;
- он отслеживается Git;
- путь совпадает с кодом;
- pubspec.yaml включает необходимую asset-директорию;
- Flutter Web build реально содержит нужный asset.

Локально существующий, но не попавший в Git файл
НЕ считается завершённой работой.


## 6. Flutter

Основной стек:
Flutter + Flame.

Не добавлять Web-only реализацию,
которая ломает будущий Android или iOS,
если пользователь явно этого не просил.

Проект в будущем должен выпускаться:
- Web;
- Android / Google Play;
- iOS / App Store.

При необходимости platform-specific решения
изолировать корректным способом.


## 7. Обязательные проверки ПОСЛЕ изменений

Перед commit обязательно выполнить:

flutter pub get
flutter analyze
flutter test
flutter build web --release

Работа НЕ считается законченной,
если analyze, tests или production Web build падают.

Не обходить тесты и не удалять тесты только ради зелёного результата.

Если тест выявил реальную проблему —
исправить её.

Если тест устарел из-за намеренно изменённого поведения —
обновлять его только если это логически обосновано.


## 8. Визуальные изменения

Если задача затрагивает:

- UI;
- уровень;
- персонажа;
- фон;
- анимацию;
- карту;
- расположение объектов;
- игровую механику;

после сборки дополнительно запустить Web-версию локально
через HTTP и визуально проверить изменённый сценарий.

Проверить:
- нужный экран;
- графику;
- отсутствие placeholder;
- загрузку ассетов;
- отсутствие критических ошибок браузера.

Не считать одну только успешную компиляцию
доказательством корректного визуального результата.


## 9. Завершение каждой успешно выполненной задачи

Если пользователь не сказал:
"не коммить", "не пушь", "покажи сначала" или аналогичное,

после успешных проверок:

1. Просмотреть git diff.

2. Убедиться, что в commit не попадают:
   - временные файлы;
   - debug-артефакты;
   - секреты;
   - ключи;
   - локальные backup-файлы;
   - случайные generated-файлы.

3. Сделать понятный commit.

4. Push в main.

5. Дождаться GitHub Actions.

6. Убедиться, что workflow:
   Build and deploy Flutter Web
   завершился успешно.

7. Убедиться, что ветка web-deploy обновилась
   сборкой именно из нового commit main.

8. Если интернет доступен —
   проверить production:
   https://bearmath.ru

9. После всего выполнить:
   git status

10. Важная работа не должна оставаться
    только на локальном компьютере.

Работа считается полностью законченной только когда:
- изменения сохранены в Git;
- main отправлен на GitHub;
- CI успешно прошёл;
- web-deploy обновился.


## 10. Если deployment упал

Если GitHub Actions не прошёл:

- НЕ считать задачу завершённой;
- изучить ошибку;
- исправить причину;
- повторить проверки;
- снова push;
- дождаться зелёного CI.

Не редактировать web-deploy вручную,
чтобы обойти CI.


## 11. Резервные копии

Основной источник проекта — GitHub.

Дополнительно существует приватное резервное хранилище:

Timeweb S3
bucket:
denis-projects-backup

структура:
Bear Game/backups/

S3 содержит milestone Git bundle backups.

Не требуется создавать S3 backup после каждой мелкой правки.

НИКОГДА:
- не сохранять S3 Access Key;
- не сохранять S3 Secret Access Key;
- не добавлять ключи в Git;
- не помещать ключи в AGENTS.md;
- не помещать ключи в код.

S3 backup выполняется отдельно по запросу пользователя
или при явно согласованном milestone.


## 12. Секреты

Никогда не коммитить:

- пароли;
- access keys;
- secret keys;
- токены;
- приватные сертификаты;
- credentials;
- содержимое .env с секретами.

Если такие данные обнаружены —
не выводить их полностью в отчёт,
а сообщить пользователю о проблеме.


## 13. Существующая инфраструктура

Не менять без отдельного запроса:

.github/workflows/deploy-web.yml
DEPLOY.md
структуру main → web-deploy
Timeweb deployment
bearmath.ru

Deployment уже настроен и работает.


## 14. Финальный отчёт пользователю

После каждой задачи сообщать кратко:

- что изменено;
- какие файлы затронуты;
- flutter analyze: результат;
- flutter test: результат и число тестов;
- flutter build web: результат;
- commit SHA;
- push в main: да/нет;
- GitHub Actions: успешно/нет;
- web-deploy обновился: да/нет;
- production проверен: да/нет;
- git status чистый: да/нет.

Не перегружать пользователя техническим логом,
если всё прошло нормально.

Если что-либо не выполнено —
прямо указать это.


## 15. Приоритет сохранности

Главное правило:

Никогда не оставлять законченную важную работу
только на локальном корпоративном компьютере.

После завершённой задачи актуальное состояние проекта
должно находиться в личном GitHub пользователя.


## 16. Изменение этого файла

AGENTS.md является инфраструктурным правилом проекта.

Не удалять и существенно не изменять AGENTS.md
без прямого запроса пользователя.
